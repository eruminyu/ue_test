# 05. 포트폴리오 발전 로드맵

지금의 SoulCombat(2026-09 기준 전투 프로토타입)을 포트폴리오로 내기 좋게 키우는 계획이다. 순서는 현재 상태 진단, 직군 결정, 공통 단계, 직군별 추가 트랙, AI로 만든 부분 다루기, 하지 않을 것, 추천 순서다.

**2026-09-30 목적 보충:** 이 문서는 포트폴리오를 만드는 경우의 제안이며, 채용 평가 기준을 검증한 자료나 언리얼 학습 필수 순서가 아니다. 사용자는 **게임 제작과 개선을 먼저 진행하고 학습은 나중에** 하기로 했다. 가능한 독립 작업은 여러 에디터로 병행한다. 이후 공부할 때 `07-study-guide.md`의 입력·피해·취소 경로와 작은 실험을 참고한다. 직군 선택, C++ 전환, 멀티플레이, 스킬 확대는 필요할 때 고른다. 이 PC의 Shipping 패키징과 PIE 재검증 결과는 `08-pc-validation.md`에 있다. 아래 진단 표는 제작 완료 당시를 기준으로 읽는다.

## 요약

- **넓히지 말고 깊게.** 던전·아이템·캐릭터를 늘리지 않는다. 처음 목표였던 스킬 시스템 하나를 대표 기능으로 만든다.
- **영상 앞부분에서 핵심 동작을 보여주는 것을 목표로 한다.** 타격감과 연출 개선은 그 목적에 맞춘 제안이다. 지금은 히트스톱, 사운드, 카메라 연출이 없고 애니메이션은 템플릿 맨손 동작이다.
- **결과물을 실행하고 이해할 수 있게 제공한다.** 패키지 빌드, 영상, 포트폴리오 문서를 따로 만든다. 이 PC의 패키지 빌드와 시작 확인은 완료했지만 배포 및 사람의 패키지 플레이 검증은 남아 있다(`08-pc-validation.md`).
- **지원 직군이 C++ 비중을 정한다.** 기획이나 테크니컬 디자이너라면 지금 구조(BP 중심)를 그대로 키운다. 클라이언트 프로그래머라면 GAS 코어를 C++로 옮기고 멀티플레이를 넣는 트랙을 더한다.
- **AI로 만든 부분은 밝히고, 직접 설명할 수 있게 만든다.**

## 1. 현재 상태 진단

### 강점 (그대로 내세울 것)

| 강점 | 근거 |
| --- | --- |
| 끝까지 도는 게임 루프 | 필드 → 게이트 → 입장 창 → 던전 방 5개 → 보스 → 클리어 → 복귀가 끊기지 않는다(04 3부) |
| GAS 구조 | 속성 세트, 어빌리티 세트 데이터 에셋, 태그 기반 캔슬 규칙(대시 > 스킬 > 가드 > 평타), 쿨다운·코스트 GE, 게임플레이 큐 |
| 모듈화 | 전투 컴포넌트 하나를 플레이어·몬스터·보스·봉인석·투사체가 같이 쓴다. 어빌리티·방·위젯은 상속 구조이고, HUD는 재사용 위젯을 조립했다 |
| 문서 | 사양(01), 에셋별 설계(02), 제작 기록(03), QA(04), 엔진 API 검증 노트 |
| 검증 습관 | 입력 없는 PIE 자동 테스트, 그래프 정리 전후 로직 동일성 검사 |
| 제작 파이프라인 | Claude + Unreal MCP로 BP 72개를 만들었다. 병렬 에디터, 주석 자동화, 그래프 배치 도구도 직접 만들었다 |

### 약점 (보는 사람이 먼저 알아챌 것)

| 영역 | 지금 상태 | 왜 문제인가 |
| --- | --- | --- |
| 타격감 | 히트스톱 없음(타격 시점을 WaitDelay로 맞춰서 시간 조절을 넣을 수 없었다). 사운드, 카메라 셰이크, 데미지 숫자 없음. 지면 넉백 12~19cm | 액션 게임 영상에서 가장 먼저 보이는 부분이다 |
| 애니메이션 | 템플릿 맨손 동작. 가드는 기 모으는 자세, 피격은 라이플용 애디티브, 무기 없음 | "템플릿 그대로"로 보인다 |
| 판정 타이밍 | 몽타주 노티파이 대신 초 단위 배열 + WaitDelay | 애니 속도나 시간 조절이 달라지면 어긋날 수 있다. 몽타주와 타이머의 시간 기준을 실험하고 판정 기준을 정할 필요가 있다 |
| 스킬 "시스템" | 스킬 3개 고정. 하나를 추가하려면 GA, 코스트 GE, 쿨다운 GE, 슬롯 연결을 손으로 만든다 | 메인 축이라고 했지만 지금은 시스템보다 "스킬 3개 구현"에 가깝다 |
| AI | 0.2초 타이머 + 대상 쪽으로 직진(내비메시 없음). 공격은 거리 조건을 순서대로 본다 | 보스전이 단조롭고 설계가 드러나지 않는다 |
| 피해 공식 | AttributeSet의 PostGameplayEffectExecute 안에 있다 | 현재 단순 공식에서 사용할 수 있는 구조다. 캡처할 속성·계산 재사용 요구가 커지면 ExecutionCalculation으로 계산 책임 분리를 검토한다 |
| 멀티플레이 | 없음 | 네트워크 권한·복제·예측을 배우려는 경우 별도 설계와 검증이 필요하다. 현재 싱글 플레이 학습의 결함으로 간주하지 않는다 |
| 결과물 형태 | 제작 완료 당시 에디터 실행만 가능. 현재 PC에서는 Shipping 빌드·시작 확인 완료, 영상과 포트폴리오 문서는 없음 | UE가 없는 PC에서도 실행하도록 패키지의 실제 조작·배포 검증을 추가한다 |
| 기여 증명 | BP 대부분을 AI(Claude + MCP)가 만들었다 | 면접에서 설계를 직접 설명할 수 있어야 한다(5장) |

## 2. 먼저 정할 것: 지원 직군

| 직군 | 심사자가 보는 것 | 이 프로젝트와 맞는 정도 | 더 필요한 것 |
| --- | --- | --- | --- |
| 전투·시스템 기획 | 설계 의도, 수치 근거, 기획서 품질, 플레이테스트로 고친 과정 | 높음. 사양서, 수치표, 캔슬 규칙이 이미 있다 | 기획서 세트, 밸런스 시트, 플레이테스트 기록(4-B) |
| 테크니컬 디자이너, 툴 | 데이터 중심 구조, 에디터 툴, 파이프라인 | 높음. 데이터 에셋과 MCP 도구가 이미 있다 | 스킬 편집기, 데이터 검증(4-C) |
| 클라이언트 프로그래머 | C++ 실력, GAS 이해 깊이, 구조 설계, 네트워크 | C++는 클래스 2개(SCAttributeSet, SCAbilitySet)이며 BP 중심이다 | C++ 코어·네트워크를 배우려는 경우 4-A를 검토한다. CLAUDE.md의 "C++ 최소" 규칙 변경은 사용자와 먼저 정한다 |

주 직군 하나와 보조 직군 하나를 고른다. 3장의 공통 단계는 어느 직군이든 한다.

## 3. 공통 단계

단계마다 끝날 때 영상 한 컷과 스크린샷을 남긴다. 언제 멈춰도 낼 수 있는 상태를 유지하기 위해서다.

### 0단계: 준비 (작음)

- 패키지 빌드(Win64 Shipping)를 지금 한 번 돌려 본다. 패키징 에러는 늦게 찾을수록 고치기 비싸다.
- 직군을 정한다(2장).
- 애니메이션을 바꿀지, 바꾼다면 어떤 팩을 쓸지 정한다. 1단계에서 몽타주에 노티파이를 찍기 때문에, 나중에 애니를 바꾸면 그 작업을 다시 해야 한다.
- 사람이 할 일: 에셋을 고르고 받는다(Fab 라이선스 동의는 사람이 해야 한다).

### 1단계: 판정 구조와 타격감 (중간)

목표: 영상 30초만 봐도 손맛이 느껴지게 한다.

- **판정을 노티파이 기반으로 바꾸는 안을 검토한다.** 쓰는 몽타주를 `/Game/SoulCombat`로 복제하고 노티파이 스테이트 3종을 시험한다: `ANS_HitWindow`(판정 구간), `ANS_ComboWindow`(다음 입력을 받는 구간), `ANS_CancelWindow`(캔슬 허용 구간). 어빌리티는 WaitDelay 배열 대신 게임플레이 이벤트를 기다린다. 애니메이션 시간에 판정을 연결하는 방법이다. 배속·히트스톱·블렌드아웃·행동 취소 때 이벤트 수신과 정리까지 검증해야 한다.
- **히트스톱**: 타격 순간 공격자와 피격자의 CustomTimeDilation을 짧게(0.05~0.12초) 낮춘다. 타격 종류별 값은 데이터로 둔다.
- **카메라**: 타격 세기별 카메라 셰이크, 피니시와 스킬에 FOV 펄스.
- **피격 표현**: 피격 플래시(오버레이 머티리얼), 데미지 숫자(가드·크리티컬 색 구분), 콤보 카운터 HUD.
- **사운드**: 휘두름, 타격, 가드, 스킬, 보스 사운드. 이미 있는 게임플레이 큐에 붙이면 된다.
- **넉백**: 지면 넉백에 작은 띄우기를 섞거나 루트 모션 넉백으로 바꿔 체감 거리를 늘린다(지금 12~19cm).
- **슬래시 트레일**(Niagara 리본).
- 완료 기준: 같은 장면의 개선 전·후 비교 영상. 포트폴리오에 그대로 쓴다.
- MCP로 되는지 먼저 확인할 것: 몽타주 노티파이 추가, Niagara와 카메라 셰이크 에셋 편집. 안 되면 UI 자동화나 사람 작업으로 한다.

### 2단계: 스킬 시스템을 시스템으로 (큼, 대표 기능)

목표: 스킬 하나를 추가하는 일이 "데이터 에셋 하나 + 어빌리티 하나"로 끝나고, 플레이어가 스킬을 고르고 키울 수 있다.

- **스킬 정의 데이터**: 스킬마다 데이터 에셋 하나(이름, 아이콘, 설명, 어빌리티 클래스, 코스트, 쿨다운, 레벨별 계수 커브, 캔슬 등급 태그, 선행 스킬). HUD 슬롯, 툴팁, 스킬 창이 모두 여기서 읽는다.
  - 어빌리티 클래스 참조 변수는 MCP로 만들 수 없다. BP로 가려면 사람이 에디터에서 변수 하나만 만들어 주면 된다(1분). C++로 가려면 `SCAbilitySet`처럼 구조체를 추가한다. 어느 쪽이든 CLAUDE.md 규칙대로 먼저 정한다.
- **GE 정리 후보**: 스킬마다 따로 있는 코스트·쿨다운 GE를 SetByCaller 공용 GE로 합치는 방법을 검토한다. 값은 스킬 데이터에서 넘기되, 공용 비용 GE로 바꾸기 전에 SP 부족 시 발동 거부와 Commit/차감/쿨다운 순서를 설계한다. 기본 `CheckCost`는 별도 Spec으로 검사하므로, 나중에 피해 Spec처럼 SetByCaller 값을 넣는 것만으로 비용 검사까지 해결되지 않는다. 근거와 실험 방향은 `07-study-guide.md` 4장에 있다.
- **성장과 선택**: 스킬 레벨과 스킬 포인트, 선행 조건이 있는 스킬 트리 창, 드래그 앤 드롭 슬롯 교체. UI 모듈화를 보여주기 좋다.
- **스킬을 3개에서 8개 안팎으로, 종류를 다양하게**: 카운터(가드 성공 직후 입력), 차지(누른 시간에 따라 변화), 공중 추가타(띄운 적 대상), 설치형, 버프, 게이지를 모아 쓰는 궁극기.
- **캔슬 고도화**: 캔슬 구간은 노티파이로, 캔슬 규칙은 표(데이터)로 둔다. 스킬 → 스킬 연계 보너스를 넣는다. 저스트 가드와 저스트 회피(짧은 판정 창 + 슬로우모션 보상)도 넣는다.
- **상태 확장**: 띄우기 → 공중 추가타 → 다운 → 기상 무적. 적에게는 슈퍼아머와 그로기 게이지.
- **디버그 오버레이**: 현재 태그, 캔슬 가능 여부, 쿨다운, 입력 큐를 화면에 띄운다. 시스템 설명 영상에 그대로 쓴다.
- 완료 기준: 새 스킬 하나를 추가하는 과정을 단계별로 보여줄 수 있다.
- 선택: 두 번째 캐릭터를 스킬 세트와 스탯 데이터만 바꿔서 추가한다. 모듈화를 가장 확실하게 증명한다.

### 3단계: 적과 보스 (중간~큼)

- AI를 StateTree로 옮긴다(GameplayStateTree 플러그인은 이미 켜져 있다). 상태도가 그대로 설계 문서가 된다.
- 내비메시로 이동하고, 여러 마리가 플레이어를 둘러싸게 한다(EQS는 선택).
- 보스: 페이즈 3단계, 패턴 테이블(가중치, 쿨다운, 거리 조건), 그로기 게이지(깨면 다운 + 추가 피해), 패턴 전조(예고원 + 섬광 + 사운드).
- 역할이 다른 몬스터 1~2종: 원거리형(대시로 파고들게 만든다), 돌진형(가드를 강제한다).
- 던전 결과 랭크: 클리어 시간, 피격 횟수, 최대 콤보.

### 4단계: 보이는 품질 (중간, 사람 비중 큼)

- 애니메이션 교체: 검을 든 캐릭터, 가드·피격·다운·기상 전용 모션(IK 리타기팅).
- 레벨 아트: 무료 환경 에셋으로 던전을 꾸미고 라이팅과 포스트 프로세스를 맞춘다.
- UI 아트: 스킬 아이콘, HUD 톤 통일.
- 에셋 선택과 받기는 사람이 한다. 배치와 설정은 MCP로 돕는다.

### 5단계: 포장 (중간, 가장 중요)

- **빌드**: Win64 Shipping 빌드를 GitHub Releases나 드라이브에 올린다. 저장소에는 템플릿 콘텐츠가 빠져 있어서 심사자가 해 볼 수 있는 것은 빌드뿐이다.
- **영상**
  - 60~90초 하이라이트. 첫 10초에 가장 화려한 장면을 둔다.
  - 3~5분 시스템 설명. 디버그 오버레이를 켜고 자막을 단다.
  - 1단계의 개선 전·후 비교.
- **포트폴리오 문서**(PDF 10~15쪽): 1쪽 요약(역할, 기간, 도구, 영상 링크) → 핵심 시스템 3개 구조도 → 문제 해결 사례 3~5건 → 회고.
  - 문제 해결 소재는 03·04 문서에 이미 있다.
    - 콤보 입력 버퍼를 bool에서 큐로 바꾼 것
    - 플레이어가 트리거 안에서 태어나 방이 시작되지 않던 문제
    - GAS 입력 이벤트와 어빌리티 발동의 순서
    - 컨트롤러 없는 더미가 넉백되지 않던 문제(`bRunPhysicsWithNoController`)
    - 판정 타이밍을 노티파이 기반으로 바꾼 이유(1단계)
- **README**: GIF, 구조도, 빌드 받는 곳, 본인이 한 부분.

## 4. 직군별 추가 트랙

### 4-A. 클라이언트 프로그래머

지금 규칙("C++는 GAS에 꼭 필요한 것만")을 "C++ 코어 + BP 데이터·연출"로 바꾼다. 이 역할 분담 자체가 면접 이야깃거리다.

- **C++로 옮길 것**
  - ASC 서브클래스와 입력 태그 처리(지금은 AC_CombatComponent)
  - 어빌리티 베이스(GA_SCBase, GA_ActionBase의 공통 부분)
  - 커스텀 AbilityTask: 콤보 입력 대기, 판정 구간 대기 + 무기 궤적 스윕(프레임 사이 보간)
  - 피해 계산을 GameplayEffectExecutionCalculation으로(방어, 가드 배율, 크리티컬)
- **BP에 남길 것**: 수치, 몽타주와 큐 연결, 연출, UI
- **멀티플레이 2인 협동(리슨 서버)**: 어빌리티 예측(LocalPredicted), 몽타주와 루트 모션 복제, 쿨다운 예측. GAS를 쓴 이유를 가장 확실하게 보여주는 소재다. 규모가 크다.
- **성능**: Unreal Insights 캡처, 투사체와 데미지 숫자 오브젝트 풀링.
- **테스트**: 지금의 PIE 테스트 드라이버 BP를 Automation 또는 Functional Test로 옮긴다.
- 핵심 C++는 본인이 직접 쓰고, AI는 리뷰와 보조로 쓰기를 권한다(5장).

### 4-B. 전투·시스템 기획

- **기획서 세트**: 전투 시스템, 스킬(스킬별 의도, 프레임표, 수치, 캔슬), 몬스터·보스 패턴, 던전 레벨(평면도는 `docs/screenshots`에 있다).
- **밸런스**: 스프레드시트 → CSV → DataTable 파이프라인, DPS·처치 시간 계산표, 목표 클리어 시간과 실측 비교.
- **플레이테스트**: 5명 이상 관찰·설문 → 수정 → 다시 측정. 전후 수치를 문서에 남긴다.
- **레퍼런스 분석**: 소울워커 같은 액션 RPG의 스킬·캔슬 구조를 비교하고, 이 프로젝트가 왜 그렇게 골랐는지 적는다(1~2쪽).

### 4-C. 테크니컬 디자이너, 툴

- **스킬 편집기**(Editor Utility Widget): 스킬 데이터를 편집하고 바로 미리보기로 재생한다.
- **데이터 검증**: 스킬 데이터 누락이나 태그 오류를 저장할 때 경고한다.
- **AI 제작 파이프라인 사례 연구**: MCP 쿡북, 그래프 로직 동일성 검사, 병렬 에디터, 주석 자동화. 무엇이 되고 무엇이 안 됐는지, 어떻게 우회했는지 적는다.

## 5. AI로 만든 부분 다루기

지금 BP 대부분은 Claude가 Unreal MCP로 만들었다. 포트폴리오에서는 이 사실을 밝히기를 권한다.

- 숨기면 위험하다. 면접에서 그래프 하나를 열고 "이 노드는 왜 여기 있나요?"만 물어도 드러난다.
- 회사마다 AI 활용을 보는 시각이 다르다. 가점으로 보는 곳도, 경계하는 곳도 있다. 공고와 회사 분위기를 보고 얼마나 앞에 내세울지 정한다.
- 역할을 나눠 적는다. 본인이 정한 것(게임 사양, 캔슬 규칙, 수치, 검수와 수정 지시)과 AI가 구현한 것을 구분한다. 팀 프로젝트라면 팀원별 기여 표도 둔다.
- 앞으로는 지원 직군의 핵심 부분을 본인이 직접 한다. 프로그래머라면 C++ 코어, 기획이라면 기획서와 수치다.
- 셀프 점검: 면접 예상 질문 목록을 만들어 답해 본다. 예:
  - 왜 GAS를 썼나? 어빌리티 인스턴싱 정책은 왜 InstancedPerActor인가?
  - 입력 태그 이벤트를 TryActivateAbility보다 먼저 보내는 이유는?
  - 1~3타는 섹션 점프인데 4타만 몽타주를 바꾼 이유는?
  - 캔슬 우선순위를 태그로 어떻게 구현했나?
  - 콤보 입력을 bool에서 큐로 바꾼 이유는?
  - 전투 컴포넌트와 캐릭터 상속은 역할을 어떻게 나눴나?

## 6. 하지 않을 것

들이는 비용에 비해 효과가 작다. 전투 포트폴리오에서는 거의 평가받지 않는다.

- 인벤토리, 장비, 상점, 퀘스트, 재화. 스킬 성장에 필요한 스킬 포인트만 둔다.
- 던전과 맵 추가. 던전 하나를 완성도 있게 만드는 편이 대충 만든 세 개보다 낫다.
- 캐릭터 여러 명. 예외는 데이터만으로 추가하는 두 번째 캐릭터(2단계 선택 항목)다.
- 오픈월드, 대규모 저장 시스템.
